## Trusted setup ceremony posture

S1 **inherits** the upstream anoncitizen circuit's trusted setup. We do
**not** run our own Powers-of-Tau or phase-2 contribution ceremony in
S1 for three reasons:

1. The upstream ceremony already includes ≥ 64 contributors (verifiable
   per the anoncitizen repo's `ceremony.json`).
2. Running our own ceremony adds 2–3 weeks of timeline and a launch-
   blocking coordination dependency.
3. Our threat model assumes the **circuit** is the trust root; running
   the same setup again does not reduce risk if the upstream ceremony
   was honest, and adds risk if our ceremony is not.

What we commit to:

- **Verifying key (`vkey.json`) is committed to the repo** at
  `packages/contracts/src/verifier/vkey.json` and its SHA-256 is **pinned
  on-chain** as a `bytes32` constant in `CitizenVerifier.sol`.
- The contract verifies the pin in its constructor; a mismatched
  `vkey.json` at deploy time aborts deployment.
- The proving key (`.zkey`) SHA-256 is pinned in
  `packages/shared/constants/zkp.ts` and integrity-checked on first load
  by every client (web WASM bootstrap, mobile prover router).
- If upstream rotates the setup, we cut a new contract (do not upgrade
  the verifier) — nullifiers from the old contract are **not** migrated
  in S1. Migration is an S2 ADR (see open questions).

## Nullifier formula

From the [ZKP research wiki](https://github.com/facktivist/factivist/wiki/Research-Anoncitizen-ZKP):

```
nullifier = Poseidon(
  seed,
  Poseidon(photo[0..15]),
  Poseidon(photo[16..31])
)
```

Where:

- `seed` is a citizen-chosen 254-bit field element (kept on-device,
  never transmitted).
- `photo[0..31]` are 32 bytes from the citizen's Aadhaar photo
  (downscaled, deterministic crop). The full photo is **not** an input.

**The citizen's Aadhaar number is not in the nullifier input.** This is
deliberate — Aadhaar numbers have a 12-digit input space that is
trivially enumerable, which would defeat the unlinkability guarantee.
The Factivist vision doc §3.3 currently states the opposite and needs
correction; tracked as a **residual action** in §Open questions.

## Proving stack split

Per [[ADR-011]] (hybrid proving) and Phase 3 decision D2 (now [[ADR-018]]):

| Platform | Prover | Why | Where the inputs live |
|----------|--------|-----|-----------------------|
| **Web** | snarkjs WASM in a Web Worker | Off the main thread; works on any modern browser without native deps. | Browser memory; cleared on tab close. Never sent to server. |
| **iOS** | rapidsnark via Expo native module | iOS A12+ proves in ~6 s; rapidsnark is the fastest mobile option. | Device memory; cleared at app background. |
| **Android (mid + high tier)** | snarkjs JS via Hermes | Pure JS, ships with the Expo bundle; ~14 s on mid-tier. | Device memory; cleared at app background. |
| **Android (low tier, opt-in)** | **Server-side fallback** at `apps/api/src/routes/identity/prove` | Devices < 3 GB RAM cannot complete in < 60 s. Without fallback, ~30% of Indian users are excluded. | See §Server-side fallback below. |

The mobile prover router (`apps/mobile/src/features/identity/proving.ts`)
selects platform via `Platform.select` + a runtime RAM probe; user is
prompted with a **consent dialog** ([[ADR-018]]) before any input leaves
the device.

## Server-side fallback key custody

This is the single S1 path on which proof inputs cross the citizen ↔
server trust boundary. It is treated as a **residual risk R-1** in
[`threat-model.md`](./threat-model.md).

**Rules of custody**:

1. **Ephemeral prover**: a dedicated Hono route
   (`POST /identity/prove`) accepts the proof inputs, generates the
   proof in-process (rapidsnark on the API host), returns the proof, and
   **drops the inputs from memory**.
2. **No persistence**: inputs (the citizen's Aadhaar photo bytes + seed)
   are **never** written to Postgres, Storage, or disk. The Bun process
   holds them in memory for the duration of one request and overwrites
   the buffer before reply.
3. **No logs of inputs**: the `audit_log` row for this route records
   `request_id`, `outcome ∈ {ok, fail}`, `latency_ms`, and the resulting
   `nullifier` — **never** the inputs. The Hono request logger is
   configured with an explicit allowlist for this route.
4. **Sentry scrub**: a `beforeSend` hook drops any breadcrumb whose
   payload references the prove route's body field names.
5. **Consent UI required**: the mobile client must surface the consent
   dialog ([[ADR-018]]) before invoking this route; the route rejects
   requests missing the `X-Consent-Acknowledged: 1` header.
6. **Rate limit**: 1 attempt / device-fingerprint / hour to reduce abuse
   surface; failure does not retry automatically.

## On-chain verifier custody

`CitizenVerifier.sol` is the only contract in S1 ([[ADR-003]]).

| Operation | Authority required | Mechanism |
|-----------|--------------------|-----------|
| Deploy | K-4 (one-time burner) | Hardhat deploy from cold EOA; deployer renounces ownership in the same transaction by transferring to the 2-of-3 Safe multisig. |
| Upgrade verifier (e.g. new vkey) | 2-of-3 multisig (K-3) | UUPS proxy pattern via OpenZeppelin; **7-day timelock** between proposal and execution. |
| Pause (emergency) | 2-of-3 multisig (K-3) | `pause()` is **not** timelocked; takes effect immediately. Unpause requires same multisig. |
| Add nullifier | Internal only — gated by `verifyProof` | No external `addNullifier` call exists. |
| Read nullifier set | Public | Free RPC + The Graph mirror. |

**Multisig signers**: 3 named officers — **TBD**. Phase 5 issue
(`security:multisig-signers`) must (a) pick signers from 5 candidates,
(b) onboard each onto a Ledger, (c) run a tabletop exercise with one
signer offline, (d) publish anonymised role descriptions (not addresses)
in the public repo.

### Incident playbook (single-key leak)

Run the matching row. Each row references the runbook PR that must
exist before launch (Phase 5 deliverable).

| Leaked key | Immediate (≤ 1h) | Short-term (≤ 24h) | Postmortem |
|------------|------------------|--------------------|------------|
| K-3 officer key | Multisig replaces that officer (still 2-of-3 with the remaining 2); rotate to new 2-of-3 within 7 days. | Audit `NullifierAdded` events for the window of compromise — no false positives possible (proof is still required), but log the bounded risk. | Public post-mortem (no officer identity disclosed). |
| K-4 deploy EOA | N/A — burnt post-deploy. If leaked **before** deploy, generate a new EOA, redeploy. | — | — |
| K-5 Supabase service role | Rotate via Supabase dashboard; redeploy `apps/api`. | Audit `audit_log` for unexpected admin actions; restore from backup if any tampering detected. | Public post-mortem. |
| K-8 Cloudflare token | Revoke at Cloudflare; rotate. | Audit zone change history. | Public post-mortem. |
| K-9 CF↔origin secret | Rotate both ends; old secret rejected immediately. | Confirm no direct-origin traffic served during the window (Fly.io logs). | Internal post-mortem. |
| K-10 session HMAC | Rotate; all citizen sessions invalidated; users re-prove. | UX banner in onboarding flow explains re-verification. | Internal post-mortem. |
| K-12 Android keystore | **Critical** — cannot rotate without a new app listing. Trigger Google Play key reset procedure; new APK upload. | Coordinate with mobile lead; communicate via official channels. | Public post-mortem. |
| K-1 / K-2 (proving / verifying key) | Pause `CitizenVerifier.sol` (multisig); halt new verifications. | Re-pin to a clean upstream release; deploy a **new** contract (no upgrade) and migrate nullifier set per S2 ADR. | Public post-mortem with circuit-level analysis. |

### Loss-of-key incident (not leak, loss)

| Lost key | Effect | Recovery |
|----------|--------|----------|
| Single multisig officer key (K-3) | Still 2-of-3 — no immediate impact. | Add replacement signer; rotate. |
| **Two** multisig officer keys (K-3 × 2) | Verifier is frozen — no upgrade, no pause. | The contract remains operational for verify (the only critical path); cut a new contract on S2 with a new multisig, leaving the frozen one to drain. |
| K-5 (Supabase service role) | Recoverable from Supabase dashboard. | Reset, redeploy. |
